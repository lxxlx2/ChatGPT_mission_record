本设计保持原实验的 *硬上限而非默认执行量*：三条**总**在途槽位（HEAD也占槽位），`eth_chainId` 1次、初始 `eth_blockNumber` 1次、刷新HEAD ≤6次、完整区块请求 ≤24次、**全部 RPC 尝试 ≤32次**；所有方法共用请求**实际开始**时间间隔至少250ms。每个请求原始 HTTP body 上限2,000,000 bytes、每个请求超时上限5000ms、发起窗口 ≤60s、HEAD 自最近成功完成到下一次BLOCK派发的新鲜度 <4000ms。只允许 BSC `chainId=56`、`eth_chainId/eth_blockNumber/eth_getBlockByNumber(height,true)`。没有自动重试，没有 WS、代理、重定向、付费回退、交易/签名、后台常驻、计划任务或附加 RPC。

**这些数字是后续代码不得超过的设计界限，并不表示任何数量已获得使用授权。** 实际真实试验需要单独、明确的新许可（允许更小数额），不能复用已经消耗的历史批准。

## 二、拟实现模块边界和状态机

独立的新模块（名称暂定，后续新 PR 才创建）：
- `f0_l2_transport_one_shot.py`：唯一具备网络能力的入口；缺少新的明确 `--execute-live` + 验证通过的**双独立批准** + 固定 Git SHA 等条件时，启动前即拒绝；导入不发请求。
- `f0_l2_coordinator.py`：单协调者负责独占分配请求 ID、共享槽位、全局发送间隔和全部预算；不同线程/任务**不得**自行预留、刷新 HEAD 或独立限速。
- `f0_l2_attempt_ledger.py`：私有独占日志和原始响应归档。单一写入者/受锁临界区负责串行 fsync，每个在途请求都有不可复用ID，完成回包可乱序。
- `f0_l2_grant_gate.py`：只负责读取并验证*外部*批准和一次性租约消耗；不得自动构造获批许可或批准自身；签名/审批凭证的身份真实性必须先有独立代码审查和可重复的负例证明。
- `f0_l2_http_sender.py`：仅接收协调者发来的**已经持久预留**的一个只读 JSON-RPC 请求。固定 HTTPS 域名 `ENDPOINT`；验证 TLS证书/域名、禁止系统代理和重定向、拒绝压缩和超2MB读取、固定单次超时，不允许环境变量/配置指向任意URL。真正的socket逻辑和全部依赖必须列入固定SHA审核范围。

`PREPARE` → 读取**审核过的精确代码和数据字节** → 校验新用户/独立审查者的两份审批与同一许可字节hash → 固定全局 grant 消耗占用 → 建新0700私有 evidence → `INITIAL_CHAIN/HEAD` → `RUNNING` → `STOP_DISPATCH` → `DRAIN_INFLIGHT` → `SEALED`。任何 PREPARE 失败：**零网络请求**。任何未识别异常/进程崩溃：保留 UNKNOWN，**不得重启沿用许可**。未审代码变化：立即拒绝。

### 单协调者请求事务（严格顺序）

1. 从最新**已成功完成**的 HEAD 和单调时钟决策；读取高度不能超过 HEAD；等待刷新中的旧HEAD并不会延长新鲜度。每次派发前检查许可时间窗、60s发起期限、所有分类剩余预算、共享3槽、距上次实际起始≥250ms。
2. 唯一协调者保留请求ID及方法/高度，**全局预留预算**，把 `RESERVE_UNKNOWN`（包括许可hash、ID、HEAD样本和时间信息）写入0600不可覆盖日志并 fsync 文件与目录；只有持久化成功才交给 sender。预留/发送边界的异常**宁可多收费记录、不可漏计外发**。
3. sender 按受审 endpoint 发出一次请求，不自行重试。结果可为 200 JSON-RPC、HTTP错误、timeout、网络错误、截断、非法ID、非法字段等。所有已预留尝试即使失败或超时也消耗预算。
4. 原始响应字节与摘要落在0700目录下的独占0600文件，先文件和目录 fsync，之后按原请求 ID 写 `SETTLE`。即使没有响应体也记录超时/失败。若原始证据落盘失败，保留不确定结果并停止后续派发；不能报告成功，也不能重试补账。
5. 正常完整区块先算 `RPC_RESPONSE`/已解析块；依照 **原始请求ID和高度** 放入有限乱序缓冲，只有高度连续且内部父哈希相符才独立 `COMMIT_CONTIGUOUS`。父哈希错误独立记录一次 `CHAIN_INTEGRITY_FAULT`，归属坏块原ID，不污染触发检查的别的成功请求。首块若无额外外部父块，明确 `FIRST_PARENT_UNANCHORED`，不谎称外部链连续性。
6. HEAD失败/过期、响应身份问题、已尝试缺口、父哈希错误、许可/预算/时长耗尽等触发 STOP_DISPATCH，**停止新派发**，已经在途的响应按真实结果继续结算至超时或截止。一次性租约保持 CONSUMED；不因正常结束、退回、进程退出而复用。
7. 结束后封存原始字节与sha256清单、完整已尝试/失败/未尝试/未知账本、状态机转换和脱敏报告。遇到遗漏、审计矛盾或未结算 UNKNOWN → `INVALID_FOR_PERFORMANCE_CLAIM`，**不可**据此估算持续追平。

## 三、一次性用户许可：与输出目录隔离（方案必须独立审核）

新许可不在此 PR 生成。后续真实阶段才允许用户显式批准**精确 SHA + exact permit SHA256 + endpoint + 限额 + UTC起止 + 本机证据路径 + 一次性grant ID + 明确允许的网络方法**。独立审核者另行在固定 SHA 上检查实现、测试与许可字节，出具明确审查结论；通过代码审核≠通过许可审核。不能凭 `user_authorized:true` 自我断言，不能凭本地可自行编辑的单行 `APPROVE_PERMIT <hash>` 文件替代有身份约束的用户授权。许可验真方式必须另行成文、实施并有伪造/换身份反例；未验证身份时不得执行。

**推荐消耗位置**：Mac 本机用户账户下固定私有注册目录（例如 `~/Library/Application Support/MissionEvidence/f0-grant-registry/`，实际路径经审核固定），严格目录/父路径权限和非符号链接，不依赖每次可换的 `storage_root`。以 grant ID + permit 字节hash创建独占 `O_CREAT|O_EXCL|O_NOFOLLOW` 消耗记录，并在发送任何HTTP请求前 fsync 文件与父目录；不同进程互斥竞争时只能一个赢。审查者需验证**相同 grant 换输出目录、进程/主机重启、重复复制 permit、并发两个进程、异常终止、伪造/缺少签署**均不能放行。尤其不得仅依据在临时目录里是否已有 journal 判定“未使用”。如果本机消耗登记丢失、无法锁定，**fail closed**；不得自动清空或重建已消耗状态。

推荐将许可截止时刻检查成 UTC wall-clock（受系统时钟异常保护），运行时限和起始速率使用 monotonic；许可包含足够的在途超时收尾窗口。审核 SHA 锁定入口、传输、调度、解析、许可、归档及引用的数据文件，所有实际本地字节需与 Git 精确一致且 checkout clean；锁定全依赖文件，不允许临时替换 sender 回调。

## 四、不可误读的性能与积压证据

关键指标必须分开显示，不得仅报告“3个并发”或“收到N块”：
- `requests_reserved`、`requests_physically_started`（若可证实）、`settled`、`failed`、`timeout`、`UNKNOWN`；各方法预算、并发峰值、所有请求**实际开始间隔**、HTTP状态及每请求 P50/P95。
- 独立于解析成功的 `parsed_full_blocks`、`contiguous_parent_verified_commits`、`first_parent_anchor_status`、`attempted_invalid_heights`、`known_unattempted_to_last_HEAD`、`reorder_buffer_peak`、`buffer_oldest_wait_ms`。
- 每个已成功完成 HEAD 的高度和本机时间、样本首尾的来源增长速度、最新采样 HEAD − 连续提交高度、样本起始/结束与最后一次请求结算时间。**最后采样积压为0只表示对最后已知HEAD无欠账，不意味着赶上现实网络HEAD。**
- 端到端吞吐的分母必须是相同范围、相同窗口且完整结算的墙钟时间；额外报告停止原因、源端 HEAD 刷新开销、未使用区块预算及最终源头是否未知。不得用坏帧之后预先计算的派发轨迹替代实际闭环记录。
- 即使某次 ≤32调用的短窗口 `contiguous_commit_bps / observed_head_growth_bps >=1`，也仅能得出该**窗口样本**暂未落后；并不证明长期追平、免费端点稳定或交易盈利。若样本中仍 <1 或样本积压增长，只记录 `F0_NOT_PASSED`，不扩大许可自动追试。
