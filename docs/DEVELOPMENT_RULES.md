# 开发与 AI 协作交付规则（Canonical Development Rules）

**状态：生效中的仓库级开发规范**  
**范围：整个 `lxxlx2/ChatGPT_mission_record` 仓库；Frank、Monster、地址分析、ICO/Token 研究、监控与衍生工程。**  
**入口：根目录 `AGENTS.md`；人类索引 `README.md`。**

## 1. 交付介质：GitHub-first（强制）

1. 开发、修复、审核涉及的代码、脚本、测试、工作流、规则或文档，必须首先成为**仓库里真实可读、可追溯的提交**；并明确分支、PR、完整固定 commit SHA 与基线。聊天附件、临时路径、Issue 讨论与本地文件只是辅助证据，**不能取代源码交付**。
2. **禁止常规使用压缩包让用户手动下载、解压，再转交 Mac/Claude/Codex。** 尤其不能连续多轮用 ZIP 转运开发成果。即便助手有文件创建工具，也应先使用 GitHub 提交工具交付。
3. 只有**用户明确提出离线文件包**，或**GitHub 客观不可用且用户同意离线替代**，方可例外。即使例外，也必须保留具体文件 SHA、来源、风险和后续补入 Git 的路径；不可默默把 ZIP 当成默认方案。
4. 用户的正常操作应仅为转发 GitHub 地址和一段可复制的执行提示词。**不得把文件搬运、解压或代码粘贴变成用户的日常职责。**

## 2. 提交、分支与固定版本

1. 优先在正在使用的原 PR 修复问题；如需与已获独立批准的产品 SHA 分开审核执行器，可在其精确基线上创建**最小** Draft PR。禁止重复创建与已有 PR 同范围的工作分支。
2. 除用户明确授权的规则维护等例外，不自行合并、关闭或改变生产分支。代码审核采用独立 checkout、detached 固定 SHA；审核前后核对远端 HEAD、base、Draft/merged 状态。
3. 报告须区分来源：`GitHub code/CI`、`Mac isolated/offline`、`live read-only`、`production effect`。每个 PASS 必须指向实际做过的验证；不可拿 GitHub CI、合成 fixture 或旧快照代表生产。
4. 当代码发生变化时，旧 SHA 的 APPROVE 不会自动延伸到新 SHA；若存在 P0/P1/P2，先记录真实反例及最小修复，按新 SHA 审核。

## 3. 向 Mac Codex / 其他 AI 交接

每次需要用户转发的提示词或 zsh 命令，应优先包含：
- GitHub 仓库／PR／commit 链接、**完整固定 SHA**、比较基线和变更文件范围。
- 允许的操作、禁止的生产副作用、可访问的环境、实际目标、测试命令与退出条件。
- 使用 GitHub 固定源码建立**独立 detached checkout**；不修改正在运行的原工作区；缺少对象时如需 fetch，必须把 fetch 的 GitHub 源码范围和仅网络读取性质说清楚，不能擅自执行脚本、部署或启动服务。
- 实测环境及结果、回执链接，并通过 GitHub API 读回。Mac 提示词应兼容 zsh，避免需要用户手动搬运文件。
- 不通过 ZIP、粘贴完整程序、私人目录中的临时文件或聊天附件代替 GitHub 引用。

## 4. 生产安全与发布门禁

- 默认 `NO_DEPLOY / NO_RESTART / NO_REAL_RPC / NO_CA_POST / NO_TRADES / NO_MERGE / NO_PRODUCTION_WRITE`；通知、邮件、生产服务操作也须单独明确授权。
- **代码 APPROVE ≠ 生产授权；隔离 PASS ≠ 真实 RPC 完整覆盖；旧版源码备份 ≠ 已证明可回滚。**
- 生产发布应独立验证产品源码 SHA、执行器 SHA、实际 Mac 运行身份、旧版可运行备份、完整清单、首错留证和紧急恢复；禁止未经授权的 launchctl 或广域安装脚本。
- 若旧故障根因 `UNRESOLVED`，明确记录剩余风险并由用户选择是否接受；禁止将未知标记为已解决，禁止因为持续测试而默认获得发布许可。
- 仓库是公共仓库时只写入脱敏代码与审核证据，不上传钱包私钥、token、付费 RPC URL、生产回执原文、私有文件路径或个人敏感数据。

## 5. 用户可见的交付检查表

完成研发交接前，必须确认：

- [ ] 源码及测试**确实已经提交 GitHub**，不只是生成在临时容器或 Mac 目录。
- [ ] 给出可打开的 GitHub PR/commit URL、完整固定 SHA、基线和变更清单。
- [ ] 说明实际执行了什么测试（Mac、CI 或仅合成）；哪些没执行。
- [ ] 用户只需复制**提示词或 zsh 兼容命令**，无需手动下载、解压或传 ZIP。
- [ ] 未扩大授权、未擅自部署、重启、RPC、通知、交易或合并。
- [ ] 需要持续同步的工作写入对应 Issue/PR，并读回验证；**Issue/PR 评论不等于已经更新开发规则。**

## 6. 规则优先级和维护

- 根目录 `AGENTS.md` 是 AI 代理在仓库中的入口；本文件是仓库级开发交付规则的**正式来源**；`README.md` 必须指向它们。
- `docs/REPOSITORY_STRUCTURE.md` 负责仓库目录与命名规则；模块内的 runtime/spec/gate 负责业务与操作约束。它们与本文件并存，若出现交付或生产安全冲突，采取较严格的约束并请用户裁决。
- **永久性规则改动必须更新本文件与根 `AGENTS.md`（必要时 README）并提交到可被后续开发者读取的正式仓库分支。** 不得仅在聊天记忆、Issue/PR 评论里宣称“已写入规则”。
