# X / Crypto 技术推文写作与发布规范

Updated: 2026-10-01
Status: canonical writing rule for technical X posts

## Goal

用于项目操作记录、链上排障、脚本教程、领取/解锁/出售流程等技术型 X 推文。

目标不是“写成文章”，而是让一个完全没看过前文的人：
- 30 秒内知道这是什么项目；
- 1 分钟内知道怎么做；
- 遇到同样报错时知道怎么解决；
- 能直接拿到真实链接、脚本、合约和成功判据。

## Core rule

**项目身份先说清 → 真实入口直接给 → 按操作顺序写 → 每步给成功判据 → 报错写解决方法 → 事实和推测分开 → 删除感受和废话。**

## 1. 第一段必须说明项目身份

开头直接写：
- 项目名；
- 官方 X；
- 必要时官网；
- 当前问题或教程目的。

示例：

`UNICRED（官方 X：@UNICRED0）官网 451 后，之前质押的 NFT 仍然可以直接从 Unichain 链上取回。`

禁止只写“这个项目”“最近那个 NFT”“之前说的项目”。读者不能依赖上下文。

## 2. 有工具或脚本时必须给真实链接

只要涉及脚本、GitHub、网页工具、合约或文档，必须给可直接访问的真实地址。

禁止：
- `xxx.html`
- “去 GitHub 找”
- “自行搜索”
- “我做了一个脚本”但不给地址

推荐顺序：
1. 脚本/工具链接；
2. 下载或启动命令；
3. 本地访问地址；
4. 页面内具体操作。

## 3. 正文按用户实际操作顺序写

不要按研究过程或思考过程写。

标准顺序：

`准备 → 下载/打开 → 填什么 → 点什么 → 钱包确认什么 → 怎么判断成功`

例如：

1. 下载脚本
2. `python3 -m http.server 8080`
3. 打开 localhost
4. 输入 Token ID
5. 选择钱包
6. Claim
7. Unstake
8. `ownerOf()` 检查结果

## 4. 每一步必须有成功判据

不能只写“执行成功”“应该可以”。

优先写链上可验证结果：
- `ownerOf(tokenId) = 自己的钱包`
- `isApprovedForAll = true`
- receipt `status = 1`
- NFT Transfer 已发生
- 实际收到多少 WETH/USDC/ETH

成功判据应紧跟对应操作。

## 5. 报错统一写成：现象 → 排查 → 解决

不要写长篇背景。

推荐格式：

`报错：Not enough ETH...`

`检查：owner 正常 / approval 正常 / 实际 gas 足够`

`解决：补充原生 ETH 到某阈值后重新执行，实测成功`

如果没有确认根因，只写“workaround 实测有效”，不要写成已证明的内部机制。

## 6. 事实、推测和 workaround 必须分开

### Confirmed
可以直接写：
- 链上交易成功；
- 合约函数可执行；
- NFT 已转移；
- 收款金额；
- approval 状态。

### Inference
必须写成：
- “现象上看”
- “疑似”
- “不能证明其内部实现，但...”

### Workaround
必须说明：
- “我这边实测有效”
- “不能保证等同于根因”

禁止把一次成功 workaround 写成平台内部逻辑的确定结论。

## 7. 技术细节只保留能帮助复现的内容

应该保留：
- 官方 X / 官网；
- 链和 Chain ID；
- 公共合约地址；
- function 名；
- marketplace conduit；
- CLI 命令；
- GitHub 脚本链接；
- 费用结构；
- 最终实际到账；
- 成功判据。

默认删除或脱敏：
- 个人钱包完整地址；
- 私钥 / seed；
- 个人 Token ID，除非对教程不可缺；
- 与复现无关的 tx hash；
- 个人资金路径；
- 无关余额和历史细节。

## 8. 不写感受型内容

默认删除：
- “最大的感受是...”
- “Web3 的魅力...”
- “以后遇到这种情况...”
- “希望能帮到大家...”
- “记录一下我的心路历程...”
- 任何不影响操作和技术判断的叙事铺垫。

技术推文的结尾只需要：
- 最终结果；或
- 一行完整流程。

例如：

`Claim → Unstake → Check owner → OpenSea approval → Accept Offer`

## 9. 默认写成一篇完整短文，不拆 thread

除非内容客观上超过单篇可读长度或用户明确要求 thread，否则默认：
- 一篇完整短文；
- 不编号 1/7、2/7；
- 不让读者连续点开；
- 不重复背景。

## 10. 发布前 QA

发出前逐项检查：

- [ ] 第一段是否写清项目名和官方 X？
- [ ] 有脚本时是否给了真实 GitHub 链接？
- [ ] 所有命令能否直接复制？
- [ ] 是否按真实操作顺序排列？
- [ ] 每个关键步骤是否有成功判据？
- [ ] 报错是否直接给了解法？
- [ ] 是否把推测误写成事实？
- [ ] 是否已经脱敏个人地址、Token ID、资金路径？
- [ ] 是否删除感受、铺垫、AI 式总结？
- [ ] 一个陌生读者是否能仅凭这篇内容完成操作？

## Default output style

以后生成 Crypto / NFT / Web3 技术推文时，默认采用本规范；用户明确要求其他风格时除外。
