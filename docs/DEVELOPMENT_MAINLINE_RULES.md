# Mission 开发主线与停止规则（2026-10-19）

Status: **ACTIVE_DEVELOPMENT_PROCESS_RULE**。本规范规定 Mission 仓库后续开发的交付与优先级，不追溯修改历史证据；既有安全、数据来源、评审和交易许可要求继续有效。

## 核心目标与成果衡量

- **交付用户实际可使用的新能力**，而不是增加 PR、脚本、测试数量、审核次数或截图次数。每次迭代必须明确一个用户问题、一个可观察的功能/准确性结果和一个完成标准。
- 先核查最新 `main`、开发计划、现有代码、历史实验与**用户最新真实运行证据**；优先复用已存在的只读代码、快照和报告，不平行开发相同功能。
- **真实链上/交易所/生产本地事实、回放模型、合成测试、推断**分层标记，不用 CI 成功代表真实 Mac 验收，不用后端进程 LIVE 代替数据全覆盖，不用历史 BUY 代替可跟 BUY，不用本地模型持仓代替钱包余额。
- 优先级严格为：**直接影响真实数据正确性或核心功能的 P0/P1/P2 > 当前主线所需的实际业务功能 > 非阻断 P3 / 重复诊断 / UI 微调**。P2 应按实际风险判断是否阻断、记录后有限修复，不盲目追边界。
- 一轮工作只集中解决一个**核心业务问题**；除非真实复现的新阻断缺陷出现，不要因无关测试改造、传输层优化或新工具连锁生成多个互相依赖 PR。

## Frank V2 的唯一主线：D0 → D1 → D2 → D3 → D4

以 `crypto-300-profit-mission/meme/frank-wallet-monitor-dashboard-v2-design-2026-10-11.md` 为功能需求，不以近期截图/QA 工具代替 V2 整体验收：

1. **D0 基线**：确认真实运行代码身份、本地现存账本的窗口/覆盖率、证据可信度与已知缺口；有真实数据即可停，不反复重复已通过的 Safari/C02 场景。
2. **D1 事实账本**：每笔已索引主动买/卖、转入、转出、失败或待核交易可以关联其来源、状态和模型/信号处理结果；不得虚构漏链记录或未知成本。优先回答**2026-10-19 Mac 24h 已索引 2 笔 BUY 为什么没有产生新候选**，验证源记录与过滤/否决链，不因没有候选而擅改冻结策略。复用本地 `forward.sqlite` 和 `mission-control.sqlite` 的现有只读接口/查询；隐私脱敏、无新 RPC。单次有界事实核验即可决定下一阶段。
3. **D2 观察与持仓**：将已核实交易/持仓、转入、历史退出、未知状态分别放入**持久可用**的观察池；模型状态 != 链上持仓，证据缺失的盈亏必须显示 `UNRESOLVED`；不因为零正式 BUY 而清空观察池。
4. **D3 交易辅助/价值验收**：准确 CA、资金流、交易时间、买卖成本和可执行性；选**最少 5 个**可复现代币与公开 GMGN/FOMO/OKX 的同窗口可比功能独立校验，明确 PnL 口径与缺失来源；对冻结信号做 T+5m/15m/1h/6h/24h 可跟性/结果评估，不能以个别赢家外推。
5. **D4 整体验收与交付**：完成真实数据回放、代码独立审核、可回滚部署计划、用户明确授权后才允许合并/安装；真实 Mac 验收要涵盖整体观察池与账本，而不是只重复 C02/503 的独立页面截图。

### 阶段出口与停止

- 每阶段的出口必须包含：**实现的业务能力/真实数据证据、可复现验证、仍未证实的边界、下个具体阻塞**。否则状态为 `PARTIAL / BLOCKED`，不能写 `DONE`。
- 已经通过独立审核与真实实机验收的**同一固定版本/同一业务范围**立即停止重复截图或再造 QA；除非新数据证明功能真实退化，禁止为了提高测试数量重新开始审批循环。
- 本地无法得出结论：写 `UNVERIFIED` 并说明缺哪种现存源数据；**一次性**获取必要数据，不无期限反复让用户截图、手填 CA、运行散落补丁。
- 新代码必须先调查数据与依赖 → 设计可交付的最小改动 → 独立审核 → 真实/离线测试 → **用户批准后**部署 → 有界实测修复。优先在一条命名清晰的 Git 分支与 PR 中完成单阶段交付。
- 复杂 Git 分支与主线分叉不得盲目合并。做明确的最小依赖评估与只读预演；历史研究、其他模块及监控生产路径不受未审改动影响。
- 终局评估以交易辅助可用性、事实覆盖率/可信度、候选准确性、持仓和资金流可追溯、实际用户使用验证衡量，**不以通过的测试数量或 PR 数衡量**。
