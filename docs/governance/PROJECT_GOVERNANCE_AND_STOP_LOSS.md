## 0. 结论先行

1. 问题不是“文档不够细”，也不是“止损线不够多”。仓库里已经有大量门禁、ADR、止损和 NO_GO，但进度仍然很少。
2. 原提案提出四条待检验的治理问题，不能代替各模块真实业务状态核实：
   - **目标没有进入状态文件。** 项目目标是“扣费后可执行净收益”，但各模块的状态文件和 PR 标题里几乎没有这个指标。
   - **止损只会刹车，不会推进。** 门禁说“不能过”，却没有任何机制强制给出“现有数据下的答案”。
   - **工作以 PR 和过程产物增长，而不是以业务结论增长。** 原提案快照有 199 个 Open PR，其中 101 个标题含 “frank”，主线合并的 PR 总数只有 22（见第 1 节证据）。
   - **状态和决策存在于聊天记录里。** 每次新对话都要重新对齐，关键裁决没有可追溯的登记。
3. 本方案提出以下试行做法；初期只采用必要的人工记录，不先建设治理工具：
   1. 北极星指标与经济门禁阶梯（G0–G6），每一步都有明确的数据要求和分母。
   2. 优先复用现有模块状态与交接记录，分别登记证据结论和推进决策；`STATUS.md` / `DECISION_LOG.md` 是后续可选模板，不是新增授权门禁。
   3. 预算与止损矩阵，每个阈值都对应一个**强制动作**，动作包含“必须如实给出证据状态和是否继续的决策”。
   4. 分层测试方案（L0–L6），每层写明能证明什么、不能证明什么。
   5. 与 ChatGPT 网页端对话的固定协议：开场读取、单次只推进一个门禁、结束输出固定状态块。
   6. 治理工具暂缓（第 12 节）：初期不实施检查脚本、不建立新自动化或审查代理。

### 1.1 对“妖币有止损线，为什么也没进度”的直接回答

已有止损讨论。以下是需要避免的治理循环，**不是本轮已核实的 Monster 业务失败结论**：

> 门禁不过 → 补数据 / 补验证 → 新门禁不过 → …… 每一步都正确，但答案永远在下一步。

因此，本方案在止损之外增加了**油门规则**（第 4.1 节）：到期时必须同时报告事实 `PASS/FAIL/UNRESOLVED` 与推进决策 `GO/NO_GO`。证据不足可作出“不推进”的 `NO_GO`，但事实必须保留 `UNRESOLVED`，不得编造成来源失败。同时增加**成本指标**（cost-to-answer）：衡量“得到答案花了多少时间、请求和 PR”，而不是只看“通过了多少验证”。

## 2. 唯一目标与成功定义

### 2.1 北极星问题

> **在扣除全部成本（手续费、滑点、路由费、延迟损失）之后，按照可执行报价成交，跟随指定链上钱包的买卖是否显著优于预先定义的随机对照？**

拆分为三个必须分别回答的子问题（对应用户目标的三条）：

1. **及时性**：能否在可接受延迟内发现目标钱包本人签名的真实 BUY/SELL？
2. **可执行性**：在 60 / 300 / 900 秒延迟下，合理规模的纸面交易能否以可成交报价执行？
3. **净收益**：扣费后的收益是否优于实时随机对照组？

### 2.2 指标分母规则（强制）

任何数字都必须同时写出分母。以下区分不得混用：

| 层级 | 名称 | 含义 | 禁止误用 |
|---|---|---|---|
| L-a | `SIGNED_TX` | 目标钱包作为 `from` 发出的交易 | 不得当作买入 |
| L-b | `SWAP_CANDIDATE` | 调用已知 Router 或选择器命中的交易 | 地址命中不等于成功 swap |
| L-c | `BUY_CONFIRMED` / `SELL_CONFIRMED` | 交易成功，且收据或状态变化支持方向 | 必须有收据证据 |
| L-d | `EXECUTABLE_QUOTE` | 在指定延迟可获得的可成交报价 | V2 `getAmountsOut` 不等于 V3 或聚合器价格，更不等于成交 |
| L-e | `NET_PNL_AFTER_COST` | 扣费后的纸面收益 | 缺任一成本项则为 `UNRESOLVED` |

**规则：** 对照组也必须用同一分母定义，不能用“对照有 N 笔、目标有 M 笔”的口头比较。

## 3. 经济门禁阶梯（G0–G6）

所有模块可试用同一门禁名称，但**事实结论和推进决策必须分列**：

- **事实 `PASS`**：在明确范围和预先约定标准内，有足够证据支持通过。
- **事实 `FAIL`**：实际证据足以证明该范围内未达到标准；标注来源、时段、样本与失败条件，不外推至整个来源或所有路线。
- **事实 `UNRESOLVED`**：未测、证据不足、冲突或无法评分。到期也可以保留该结论。
- **决策 `GO` / `NO_GO`**：是否推进明确的下一阶段或动作。`NO_GO` 可因证据不足、预算耗尽或授权缺失作出，不等于事实 `FAIL`；`GO` 不授予任何 RPC、交易或部署权限。

每次同时写出范围、证据、分母、决策理由和剩余不确定性。执行中的 `IN_PROGRESS` 只是进度标签。

| 门禁 | 名称 | 回答的问题 | 进入条件 | 退出证据（必须） | 默认预算 |
|---|---|---|---|---|---|
| G0 | 冻结 | 北极星、来源、信号、对照、预算和停止条件是否固定 | 用户选择该范围试行；不追溯否定已有授权 | 复用现有记录写明参数、事实与推进决策 | 建议 3 天；不新增外部请求授权 |
| G1 | 真实来源可行性 | 实际来源在目标延迟下的吞吐、积压、覆盖与缺失是多少 | 已明确测量问题，代码审核与具体运行许可满足原合同 | **真实来源测量**、请求账本、RAW 哈希、范围和分母；fake transport 只证明代码逻辑，不能得出真实来源 PASS/FAIL | 按已有或新获明确许可，单次运行 |
| G2 | 信号正确性 | 候选能否被复核为 L-a/L-b/L-c | 所需 G1 范围证据足够且决定推进 | 分类表，附 UNRESOLVED 数量与分母 | 离线为主 |
| G3 | 可执行性 | +60/+300/+900 秒是否有可成交报价，含滑点与费用 | G2 有确认事件 | 真实报价快照、来源与失败分母；另行授权所需网络 | 按具体许可 |
| G4 | 扣费后净收益 | 成对差异及其不确定性是否支持目标组优于随机对照 | G3 有足够样本 | 预注册计划、成对结果、CI、敏感性分析；不足时 UNRESOLVED | 离线 |
| G5 | 小额实盘 | 授权实盘与纸面结论是否一致 | G4 证据支持且用户明确授权 | 成交、成本与偏差记录 | 金额由用户定 |
| G6 | 持续运行 | 长期运行是否稳定 | G5 结果支持且有持续运行授权 | 实际运行日志、故障记录与范围 | 另需授权 |

**G1 不能由 fake 吞吐或 CI 绿色代替。** 单次 chainId 成功，只能通过该次方法/连通性检查，不能通过完整区块持续采集标准。

### 3.1 每一门禁的硬规则

- 真实请求始终受**现有安全规则与具体授权合同**约束。本提案的 G0、状态文件或日志登记不额外授予权限，也不追溯撤销已批准授权。
- 一次 5 或 30 分钟的测量只能支持其预先定义的短窗口可行性问题；若证据足够，可对该限定问题给出 PASS/FAIL，不能冒充 24–48 小时观察或整个 F0 通过。
- G4 确认性分析计划应在看结果之前固定。事后分析标为探索性，不能冒充预注册验证；这不自动把市场事实判为 FAIL，可对确认性阶段作 NO_GO 并保留 UNRESOLVED。
- 预算到期必须作推进决策，但不得强制把未知事实变成二元结论。

## 4. 预算、止损与油门

### 4.1 到期必须决策，未知事实可以保留

预算到期后，在 24 小时内交付**事实结论 + 推进决策**。不允许仅以“再收集一点”拖延决策；也不允许为了结项而伪造 FAIL。

| 到期情形 | 强制动作 | 禁止 |
|---|---|---|
| 证据不足 | 事实 UNRESOLVED；决策 NO_GO（暂不推进），写明盲点、停止投入或待用户选择的最小后续动作 | 用 NO_GO 冒充来源已被证明失败；自动续期 |
| 实际测量不达标 | 针对已测范围记录 FAIL，按预设停止条件决定 NO_GO，并提出有成本上限的选项 | 从单次或过小样本推断整个公共来源不可行 |
| 真实运行中途失败 | 按原合同停止，记录请求、失败和 UNKNOWN；数据保留原样 | 自动重跑、换 nonce 续跑、改写 RAW |
| 事件样本为 0 | 对发生量如实计数；对盈利性、方向分类及根因保留 UNRESOLVED，除非另有证据 | 把零事件解释为钱包不盈利或来源失败 |

`NEED_MORE_DATA` 可作为说明，但必须同时给出 UNRESOLVED 及推进决策，不能成为无限延期理由。`NO_GO` 是对下一动作的决定，不是对来源、钱包或策略的永久定罪。

### 4.2 止损矩阵（所有阈值为建议值，需用户批准）

| 维度 | 阈值 | 触发动作 |
|---|---|---|
| 日历 | 经用户确认的阶段预算到期 | 24 小时内报告事实 PASS/FAIL/UNRESOLVED + 决策 GO/NO_GO（4.1） |
| 无进展 | 核实当前业务状态并由用户确认任务与起算日后，14 天无实质证据或决策进展 | 人工复盘，由用户选择继续、转向或停止；Monster 未核实前不启动该期限 |
| 真实请求 | 任一 UNKNOWN 结果，或请求超出许可 | 立即停止；不得重试；写 `INCIDENT` |
| 连续失败 | 达到具体运行合同约定的连续失败阈值（如 3 次） | 按合同结束本次运行；失败事实限于这批请求，来源可行性证据不足仍为 UNRESOLVED，不自动判该来源 FAIL |
| 连续 PR | 同一模块连续 3 个 PR 未新增真实数据点或业务结论 | 人工收敛至最小 A 类任务；必要的 B 类阻断修复仍可服务该任务，不为满足指标强行发真实请求 |
| PR 数量 | 单模块当前活跃范围过多，建议最多 3 项 | 人工聚焦当前主线；初期不全面清理、关闭或合并历史 PR |
| 状态词 | 新标签语义不明确 | 解释其事实或决策层级；保留原始来源标签，不为改名重做审核 |
| 决策留痕 | 明确用户裁决尚未同步到记录 | 在现有文档补记引用；不因此否定已批准授权，也不得凭补记扩大权限 |
| 经济结论 | 合格分析的 CI 上界小于 0 | 在其样本与条件范围内报告事实结果，决策可为 NO_GO；禁止事后调参伪装确认性结论 |
| 资金 | 由用户在 G5 授权中定义 | 超出即停，无自动续作 |

### 4.3 状态词分层（试行映射，不覆盖历史原文）

- 事实结论：`PASS`、`FAIL`、`UNRESOLVED`；G1 来源不足明确写 `SOURCE_UNRESOLVED`。
- 推进决策：`GO`、`NO_GO`，必须附具体下一阶段/动作与理由。
- 进度：`IN_PROGRESS`、`BLOCKED_BY_AUTH`、`BLOCKED_BY_EVIDENCE`。

## 5. 工作分类与 PR 纪律

### 5.1 工作的三类（取代旧的 `[A]/[B]/[C]` 解释，与 PR #241 保持一致）

| 类别 | 定义 | 示例 | 默认优先级 |

### 5.2 PR 生命周期

- 优先在现有分支/PR修复当前问题，复用现有交接文件登记；不以新增 STATUS 文件作为执行既有授权的前置。
- 初期不全面清理历史 Draft PR，也不自动关闭或合并。仅当历史 PR 实际阻塞当前任务时，提出有范围的整理建议，交用户裁决。
- 不允许通过新建 PR 来绕过已有的冻结 PR。
- 历史分支仍是可追溯证据，引用固定 SHA 并注明适用范围；不能把归档当作废弃既有研究。

## 7. 测试方案（分层，每层写明证明范围）

| 层级 | 名称 | 运行位置 | 网络 | 证据 | 能证明 | 不能证明 |
|---|---|---|---|---|---|---|
| L0 | 静态与 Git 校验 | 任意 | 无 | SHA、blob、工作树是否干净、文件哈希 | 代码字节与审核对象一致 | 功能正确 |
| L1 | 离线单元测试 | 任意 | 无 | 完整测试日志与 SHA256，零 SKIP | 逻辑在给定输入下正确 | 真实链上行为 |
| L2 | fake transport 集成 | 任意 | 无（注入假传输） | 场景矩阵结果：延迟、截断、断连、并发 | 调度、超时、持久化与并发约束 | 真实节点性能 |
| L3 | 本机无网压力测试 | 用户 Mac | 无 | 同 L2，附机器信息 | 本机环境下的调度与磁盘行为 | 外部来源行为 |
| L4 | 一次性真实只读运行 | 用户 Mac | 仅许可范围内 | 许可 SHA256、逐请求账本、RAW 哈希、对账 | 该时段、该来源的真实可得性 | 持续可用性、盈利 |
| L5 | 纸面回放与分析 | 任意 | 无 | 预注册分析计划、结果哈希 | 在已采集数据上的净收益估计 | 未来收益 |
| L6 | 用户授权的小额真实运行 | 用户 | 用户授权 | 成交与成本记录 | 实际执行结果 | 长期稳定性 |

### 7.1 测试纪律

1. **每个 PR 必须声明它覆盖哪几层**，未覆盖的层写 `NOT_RUN` 并说明原因。
2. **零 SKIP 是合并条件。** 有 SKIP 必须写原因，且 SKIP 的测试不计入通过。
3. **CI 绿色 ≠ 门禁通过。** CI 只证明 L0/L1/L2 在该环境下通过。
4. **测试数必须与固定 SHA 绑定。** 不得复用旧 SHA 的测试数字。
5. **fake transport 的延迟数字不得当作真实延迟。** 报告中必须标注 `SIMULATED`。
6. **严禁为了通过测试而修改门禁阈值。** 阈值变化须明确用户裁决并在现有记录留痕（已有 `DECISION_LOG` 时可用）；不得直接改写旧许可。

## 8. 证据规则

1. **运行暂存遵守原合同：** 现有 F0 许可要求 `storage_root` 位于 `/tmp/`，正式运行继续使用该许可绑定的临时私有路径、权限和原始字节，不因本方案改路径、改 Permit 或重置 nonce。长期归档另用用户指定的私有持久目录（目录 0700、文件 0600、当前账户所有），不将 `/tmp/` 当长期保存承诺。归档应在授权范围内复制并核对逐文件哈希、数量和原始来源映射；不覆盖原证据、不重写许可中的 storage_root、不把归档当成再次执行授权，也不自动删除或重建已消费标记。本轮不执行归档或清理。
2. **GitHub 只提交脱敏内容：** 汇总统计、哈希清单、测试日志哈希、结论与分母。
3. **每份证据必须有哈希清单。** 哈希清单本身也要有 SHA256。
4. **原始证据不得覆盖。** 追加写入新文件，旧文件只读保留。
5. **结论必须能被第三方用哈希复核。** 无法复核的结论标注 `UNVERIFIED`。
6. **交接摘要不是证据。** 摘要中的数字必须回到原始文件核对，核对不了就标注为转述。

## 15. 坦白：流程解决不了的事

1. **流程不能保证 AI 不漂移。** 它只能让漂移变得可见，并把裁决权留给用户。
2. **用户的裁决成本是真实存在的。** 本方案刻意把每次裁决压缩到决策卡的格式，但仍然需要用户每周花时间。
3. **市场不一定存在可盈利的 edge。** 本方案的目标是尽快报告 PASS/FAIL/UNRESOLVED 并决定 GO/NO_GO，不保证正面结论，也不强迫未知事实变成 FAIL。
4. **免费公共数据源可能根本不足以支撑毫秒级或秒级跟单。** 这一点只能由 G1 的真实测量回答，不能用文档假设。

## 附录 A：为什么不是“更详细的开发文档 + 测试方案”

更厚的文档会产生更多“合规但无用”的工作。历史 ADR、门禁和标签只能作为待核实背景，不能据此确认 Monster 当前业务失败；规则越多，也可能把时间花在满足规则上。本方案的重点是三件事：**目标指标可追溯；到期作推进决策而不伪造事实；明确用户裁决及时留痕且不追溯改写授权。**
