# Frank 模块运营模型 V1 —— 防漂移的工作方式

**状态：提案（PROPOSAL），等待用户批准后生效。**
**作者：Codex（独立复核方）。日期：2026-10-28。**
**适用范围：Frank 钱包监控 / CA 查询 / 跟单研究。不改动 `docs/DEVELOPMENT_RULES.md` 的交付与生产安全规则，是在其之上增加“目标管理层”。**

---

## 0. 一句话结论

Frank 模块漂移的根因不是“文档不够细”，而是**没有一个不可绕开的目标指标、没有硬预算、没有止损线、状态散落在 60 份文档和 100 个 Draft PR 里**。更厚的开发文档只会让 AI 有更多“合规但无用”的事可做。

**但要先回答一个反驳：Monster（妖币）模块早就有止损线、门禁和 ADR，进度反而更少。** 这个反驳是对的。Monster 的门禁每次都正确地说“不能过”（`NO_GO`、`G6 NO_GO`、`available_at=UNKNOWN`），但没有任何机制逼它“那就用现有的东西给个答案”。**止损线只会制造停止，不会制造前进。** 本方案和 Monster 的本质区别只有一条，写在第 4.0 节：**预算到期的默认动作不是“停下来问用户”，而是“强制出答案并交付能交付的东西”。** 没有这一条，本方案就是第二个 Monster。

本方案用 **4 件硬东西** 替代“更多文档”：

| # | 硬约束 | 作用 |
|---|---|---|
| 1 | **北极星问题（North Star Question）** | 每一项工作必须回答“这对回答北极星问题有什么贡献”，答不上就不做 |
| 2 | **一页纸状态文件（STATUS.md）** | 全模块只有这一个地方记录“现在在哪、下一步是什么、花了多少” |
| 3 | **预算与止损（Budget & Kill Switch）** | 每个阶段有 token/时间/PR 数上限，超了必须停下来向用户汇报，不许自动续 |
| 4 | **用户 10 分钟裁决清单** | 用户不需要读懂全部内容，只回答固定的 5 个问题即可做决策 |

## 1. 现状诊断（以 2026-10-28 仓库为准，数据实测）

| 指标 | 实测值 | 含义 |
|---|---|---|
| `meme/` 目录 Markdown 数 | 60 | 文档已经过载 |
| 全仓 Open PR | 198 | 几乎没有收敛 |
| Frank 相关 Open PR | 101，**全部为 Draft** | 没有一个 Frank PR 处于“准备合并”状态 |
| Frank PR 标题关键词 | fix 22 / feat 16 / docs 12 / research 11 / ci 11 / review 8 / gate 7 | 流程类（docs+ci+review+gate+acceptance）= 43，与业务类（fix+feat）= 38 相当 |
| 最近一次 Frank 合并 | 10 月 13 日 #41 | 两周无任何交付进入 main |
| 跟单可执行报价对（G4） | **0** | 核心问题至今未被回答 |
| 用户真实可用的新功能 | 旧 Dashboard 8766 仍是生产版本 | 用户体验两周没有变化 |

**典型漂移模式**（本轮已亲历）：

1. **用验证替代前进**：一个 D1/D2 功能经历了代码审核 → Mac 只读验收 → 503 故障注入 → 浏览器自动化 → 启动器 Node 路径修复 → OS 沙箱 → 无浏览器观察器 → 一次性真实观察。每一步都"合理"，但两周后用户仍在用旧 Dashboard。
2. **用新状态词替代结论**：`MAC_READONLY_ACCEPTANCE_PARTIAL`、`V1_PYC_REPRODUCIBILITY=PARTIAL`、`F3_V1_PATCH_AUTHORIZATION=NOT_GRANTED`。状态词越多，用户越无法判断“到底能不能用”。
3. **用安全理由无限扩大范围**：V1 的 143 个 `.pyc` 来源验证、6 个 pytest 缓存处理边界——这些对"跟到 Frank 的确定性机会并盈利"的贡献是零。
4. **关键问题被排在最后**：G4（跟单到底有没有价值）直到 10 月 28 日才拿到第一批 18 次价格请求的数据，而这是最该先做的事。

**根因**：AI 在没有硬边界时，会自然倾向于做"低风险、可量化、能写报告"的工作，而不是"高风险、答案可能是 NO、会让项目停下来"的工作。审核 AI 更是如此——拒绝永远比批准安全。

## 2. 北极星问题（North Star Question）

Frank 模块只回答一个问题：

> **"如果我在 Frank 买入后 T 秒看到通知并手动跟单 X 美元，持有到 Frank 卖出或 24 小时，扣除全部成本后，我的期望收益是正的吗？T 和 X 分别取什么值？"**

所有工作按对这个问题的贡献分为三类：

| 类别 | 定义 | 示例 | 默认优先级 |
|---|---|---|---|
| **A 类：直接回答** | 产出的结果能直接改变北极星答案 | 历史延迟敏感回测、真实延迟测量、可执行报价采样 | 最高，必须先做 |
| **B 类：回答的前提** | 没有它就无法做 A 类 | 数据完整性修复（仅限影响回测的部分）、只读观察器 | 中，只做 A 类明确需要的部分 |
| **C 类：与回答无关** | 产品打磨、流程完善、安全加固、非阻断的数据修复 | Dashboard 样式、503 降级、pyc 来源验证、F1–F3 发布管控 | **默认不做**，除非北极星答案已为 GO |

**硬规则**：
- 任何 PR、任务、提示词，开头必须标注 `[A]`、`[B]` 或 `[C]`，并用一句话说明理由。
- `[C]` 类任务在北极星答案为 `UNKNOWN` 或 `NEED_MORE_DATA` 期间**不得启动**。
- `[B]` 类任务必须指向一个具体的 `[A]` 任务编号，否则按 `[C]` 处理。
- 审核 AI 如果发现 PR 分类错误（例如把 C 标成 B），这是 P1 级问题，优先于任何代码缺陷。

## 3. 一页纸状态文件 `STATUS.md`

位置：`crypto-300-profit-mission/meme/STATUS.md`。**全模块唯一的状态来源**。其他 60 份文档降级为"历史归档"，不再作为状态依据。

固定结构，不许增加章节，每节不超过规定行数：

```markdown
# Frank STATUS（唯一状态来源）
更新时间：YYYY-MM-DD HH:MM Asia/Bangkok
更新者：GPT / Claude / Codex / 用户

## 北极星答案（1 行）
GO / NO_GO / NEED_MORE_DATA / UNKNOWN —— 一句话说明依据和最大不确定性

## 当前阶段与预算（最多 5 行）
阶段：Phase N - 名称
预算：已用 X / 上限 Y（PR 数、天数、外部请求数）
止损线：触发条件 —— 当前距离

## 本周唯一目标（1 行）
完成什么 → 北极星答案会变成什么

## 正在进行（最多 3 项）
- [A/B] PR #N —— 一句话 —— 负责 AI —— 阻塞点（如有）

## 等用户裁决（最多 3 项，每项附 2.4 节的 5 问答案）
- ...

## 本周已关闭（最多 5 行）
- PR #N 合并 / 关闭 / 归档 —— 原因

## 已知但故意不做（C 类清单，只记编号和一句话）
- ...
```

**硬规则**：
- 任何 AI 开始任务前必须先读 `STATUS.md`，结束后必须更新它（走 PR，可以是同一个 PR）。
- `STATUS.md` 不更新，任务不算完成。
- 行数超限视为漂移信号，审核 AI 应直接 REQUEST_CHANGES。
- 用户每天只需要看这一个文件。

## 4. 阶段、预算与止损（Budget & Kill Switch）

### 4.0 油门优先于刹车：到期强制出答案（与 Monster 的唯一本质区别）

Monster 的失败模式：门禁 → 不过 → 补数据/补验证 → 新门禁 → 不过 → ……每一步都正确，答案永远在下一步。

本方案的强制规则：**每个阶段的预算到期时，负责 AI 必须在 24 小时内用“已有的东西”给出该阶段的正式答案，不允许用 `NEED_MORE_DATA` 作为答案。**

| 阶段到期时 | 强制默认动作 | 禁止 |
|---|---|---|
| P1 历史回答到期 | 用当时已有的全部数据，给出 `GO` 或 `NO_GO`，附“这个答案的置信度和最大盲点”。样本少就写样本少，但必须二选一 | 回答 `NEED_MORE_DATA` 然后申请续预算 |
| P2 实时验证到期 | 用已捕获的真实 BUY（哪怕只有 1 个或 0 个）给出“P1 结论是否被推翻”，0 个样本则回答“未被推翻，但也未被验证，按 P1 结论执行” | 延长观察窗口 |
| P3 最小可用到期 | 把当时能跑的版本部署到独立端口给用户用，不等所有验收项 PASS | 再加一轮验收 |
| 任何阶段 | 若 AI 认为“现有数据真的答不了”，必须同时给出：**答这个问题最便宜的下一步是什么、花多少、答不出来就永久放弃** | 只说“需要更多数据” |

**`NEED_MORE_DATA` 只允许在阶段进行中使用，不允许作为阶段结论。** 阶段结论只有 `GO` / `NO_GO` 两个值。这条规则写死，用户可以直接拒收任何以 `NEED_MORE_DATA` 结束的阶段报告。

**为什么这不是鲁莽**：P1–P3 全部是只读研究和隔离部署，没有资金风险。真正的资金风险只在 P4，而 P4 的金额和次数由用户定。所以在 P1–P3 强制出结论的代价是“结论可能错”，而不是“亏钱”。结论错了会在 P2/P4 被推翻，这比永远没有结论便宜得多。

**“答案是 NO 也算进度”**：Frank 和 Monster 都有可能根本没有可跟的 edge。如果 P1 用 7 天得出 `NO_GO`，这是模块两个月以来第一个真正的进度——它让你停止在这上面花钱和时间。Monster 最大的浪费不是得到 `NO_GO`，而是花了太久才得到。本方案的核心指标因此是 **cost-to-answer（得到答案的成本）**，不是答案本身。

### 4.1 阶段划分（按北极星问题重排）

| 阶段 | 目标 | 退出条件 | 预算上限 |
|---|---|---|---|
| **P0 收敛** | 关掉噪音，把状态收敛到 STATUS.md | Frank Open PR ≤ 10；STATUS.md 上线；60 份文档归档索引 | 3 天，0 外部请求，不写新功能 |
| **P1 历史回答** | 用已有数据给出北极星的历史版本答案 | 对 ≥ 20 个历史 BUY 事件，在 T∈{30,120,300,900}s 下有扣费后的代理收益分布；明确 GO/NO_GO/NEED_MORE_DATA | 7 天，≤ 3 个 PR，外部请求按用户批准的单次上限 |
| **P2 实时验证** | 在真实延迟下验证 P1 结论 | 连续 7 天只读观察，捕获 ≥ 5 个真实 BUY，记录事件→通知延迟 | 10 天，≤ 2 个 PR，0 交易 |
| **P3 最小可用** | 把 P1/P2 已证实有用的信号交付到用户手上 | 新 Dashboard 替换 8766；用户用 1 周后确认"比旧版有用" | 7 天，≤ 3 个 PR |
| **P4 小额实盘** | 用户自定金额，手动跟单 N 次，记录真实净收益 | N ≥ 10 次有完整记录 | 由用户定 |

**P1 前不得进入 P3。** 这是把"先证明有价值、再打磨产品"写死。

### 4.2 止损线（Kill Switch，触发即停并汇报，不许 AI 自行决定继续）

> 止损线是刹车。刹车只在 4.0 的油门规则之下使用：触发止损后的汇报，必须**同时附带该阶段的强制答案**，不能只汇报“停了”。

| 触发条件 | 动作 |
|---|---|
| 任一阶段预算用尽但退出条件未达成 | **先按 4.0 强制出答案**，再汇报：答案是什么、置信度、最便宜的下一步、不续的后果 |
| 同一业务问题出现第 3 个 PR | 停止，合并或关闭到 1 个 |
| 同一 PR 第 3 轮审核仍 REQUEST_CHANGES | 停止，用户裁决：降级验收标准 / 换人 / 放弃 |
| 一周内 `STATUS.md` 北极星答案未变化且无新证据 | 停止，用户裁决是否继续 |
| 出现新的状态词（不在本文件词表内） | 审核 AI 直接 REQUEST_CHANGES |
| P1 结论为 NO_GO | 全模块转入"仅维护钱包观察工具"，所有跟单相关工作停止 |

### 4.3 允许的状态词表（封闭集合）

北极星：`GO` / `NO_GO` / `NEED_MORE_DATA` / `UNKNOWN`
任务：`DONE` / `BLOCKED` / `IN_PROGRESS` / `DROPPED`
审核：`APPROVE` / `REQUEST_CHANGES`
验证来源：`CI` / `MAC_ISOLATED` / `LIVE_READONLY` / `PRODUCTION`

其他一律不允许新造。需要表达细节写在正文，不造词。

## 5. 用户 10 分钟裁决清单

用户的主力沟通是跟 GPT 对话，内容多、关键时刻难判断。解决办法不是让用户读更多，而是**强制 AI 把任何需要裁决的事压缩成固定 5 问**，用户只回答这 5 问：

```
【裁决请求】PR #N / 任务名
1. 这件事属于 [A/B/C] 类，理由一句话：
2. 做完后北极星答案会从 ___ 变成 ___（如果不会变，为什么要做）：
3. 预算：需要 __ 天 / __ 个 PR / __ 次外部请求；当前阶段剩余 __：
4. 不做的后果（一句话）：
5. 我建议：做 / 不做 / 延后到阶段 __

用户只需回复：批准 / 拒绝 / 延后 / 问题
```

**硬规则**：
- GPT 任何超过 300 字的汇报，末尾必须附这 5 问；没有 5 问的汇报用户可以直接回"按清单重写"。
- 一次最多提 3 个裁决请求。超过 3 个说明 AI 没有做优先级排序，退回。
- 用户不回答的裁决请求，默认为"拒绝"，不是"默认继续"。

## 6. 双 AI 分工（按北极星重新划分，不按文件划分）

现在按文件所有权划分（Claude 管 D2、GPT 管 D1）导致两边各自把自己的文件做到"完美"，没有人对北极星负责。改为按**问题**划分：

| 角色 | 负责 | 不负责 |
|---|---|---|
| **GPT = 项目经理 + 北极星守门人** | 维护 STATUS.md；判断每个任务的 A/B/C 分类；向用户提交 5 问裁决；拒绝 C 类任务 | 不写业务代码，不做审核 |
| **Claude = 开发 + 研究** | P1 历史回答、P2 观察器、P3 最小可用的全部代码 | 不自己审核自己的 SHA |
| **Codex = 独立审核 + 对抗验证** | 每个 PR 的固定 SHA 审核；构造反例；检查 A/B/C 分类是否诚实；检查 STATUS.md 是否更新 | 不写产品代码 |
| **用户** | 回答 5 问；每周看一次 STATUS.md；决定金额和实盘 | 不读 PR diff，不搬文件，不判断技术细节 |

GPT 的角色变化最大：**从"参与开发"改为"只守目标和预算"**。GPT 写代码会让它失去守门人的中立性，这是当前漂移的直接来源之一。

## 7. 审核标准（替代"更详细的测试方案"）

审核 AI 的检查顺序**固定**，前一项不过不看后一项：

1. **分类诚实**：PR 的 A/B/C 标注是否正确？C 类是否在 P1 之前启动？→ 错则 P1，REQUEST_CHANGES
2. **STATUS.md 更新**：是否随 PR 更新？行数是否超限？→ 未更新则 REQUEST_CHANGES
3. **预算**：是否超出当前阶段预算？→ 超则 BLOCKED，交用户
4. **北极星贡献可验证**：PR 声称的贡献，有没有一个可以独立复算的数字或事实？→ 没有则 REQUEST_CHANGES
5. **代码正确性**：只在前 4 项通过后才看。P0/P1 阻断，P2 看是否影响北极星，P3 一律不阻断。

**明确禁止审核 AI 做的事**：
- 为非阻断问题要求第 2 轮以上修改
- 要求增加与北极星无关的测试覆盖
- 把"安全起见"作为 REQUEST_CHANGES 的唯一理由（必须给出具体的错误场景）
- 新造状态词

## 10. 这个方案自身的止损

如果本方案实施 3 周后：
- STATUS.md 的北极星答案仍是 `UNKNOWN` 或 `NEED_MORE_DATA`
→ 说明 4.0 的强制规则没有被执行，这是方案失效，不是数据不够。此时用户应直接宣布 `NO_GO`，模块转为纯钱包观察工具。

方案本身不豁免于止损规则。

## 11. 坦白：流程解决不了的事

两个模块进度都慢，有一部分原因任何流程都解决不了：**链上跟单的 edge 可能根本不存在，或者存在但在你能观察到的延迟下已经消失。** Frank 六币研究里 5/6 亏损、G4 里正值集中在单一案例且退出成交额只有几十美元，这些都在指向这个可能。

流程能做的只有一件事：**让你更快、更便宜地知道答案是不是 NO。** 如果你期待的是“流程做对了就会盈利”，那没有任何方案能承诺这个。本方案的承诺只是：3 周内你会拿到一个 `GO` 或 `NO_GO`，而不是第 61 份文档。

## 附录 A：为什么不是"更详细的开发文档 + 测试方案"

公司里的详细文档有效，是因为背后有三样东西：**预算（钱会花完）、绩效（人会被问责）、市场（产品卖不出去会死）**。AI 协作里这三样都不存在——AI 不花自己的钱、不被问责、不怕产品没人用。所以照搬文档形式，只会得到"合规的漂移"：每个 PR 都有测试方案、每个验收都有报告，但两周后用户还在用旧版本。

本方案做的事，是把那三样东西**人工造出来**：预算 → 第 4 节；问责 → STATUS.md 和 A/B/C 分类诚实检查；市场 → 北极星问题和 P1 前不许进 P3。
