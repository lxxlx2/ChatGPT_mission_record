## Stage sequence — never substitute CI for Review

1. **Investigate real sources first.** Record source identity, observed UTC time, slot or block, source completeness and material unknowns. Do not manufacture evidence or turn provider errors into zero.
2. **Freeze a scoped design/TODO.** Define user-visible outcome, acceptance criteria, files/shared interfaces, dependencies, read-only/production boundaries, sample provenance and exact base SHA. Keep work concentrated on the main business problem rather than speculative edge-case expansion.
3. **Implement in a dedicated Git branch / Draft PR.** Keep immutable evidence and prior reviewed PR HEAD intact. Link task to canonical TODO and document red/green tests; do not modify protected production by default.
4. **Run targeted + full regression on the exact HEAD.** Prefer genuine source fixtures; synthetic/failure-injection cases must be labeled. Test migration from actual prior SHAs for schema or source-identity changes, not merely synthetic versions generated by the new code. Record CI run, head SHA, failed/retried run provenance.
5. **Mandatory independent other-AI Review once the module reaches a usable completion checkpoint**, before declaring that module `CODE_REVIEW_APPROVED` or proceeding with dependent integration. Reviewer must be independent of the author and review **the final exact code SHA** against a stated parent/base, examine actual behavior, source/immutability/permission impacts, tests, old-source compatibility, data/identity authority and business acceptance limits. Verdict must be `APPROVE` or `REQUEST_CHANGES` with findings by priority and reproducible evidence. User-forwarded outside-AI reports are recorded as **external Review**, not fabricated GitHub Review events.
6. **Fix `REQUEST_CHANGES` on a separate child PR or controlled branch** while preserving the reviewed historical SHA. Re-run targeted/full exact-head CI and request **new independent Review** on modified product code. Documentation-only changes can be compared and scoped explicitly; changes to algorithm, schema, identity, shared API, data authority, strategy or UI require impacted re-review. Do not carry an old APPROVE over a changed HEAD.
7. **Module-level acceptance is not production acceptance.** Distinguish `CODE_IMPLEMENTED`, `EXACT_SHA_CI_PASS`, `EXTERNAL_CODE_REVIEW_APPROVE`, `BUSINESS_SOURCE_ACCEPTED`, `LOCAL_MAC_ACCEPTED`, and `PRODUCTION_RELEASE_APPROVED`. Preserve unresolved missing fixtures, stale data and business gaps, even after a valid code APPROVE.
8. **Cross-module integration Review** when combining modules sharing code or data, including Frank F01/F02, A02/A03/A04/A05, CA C01/C02 and future upstreams: create a disposable merged tree based on then-current main and exact reviewed heads; run the full real-Git tests, focused tests, public interfaces, browser/real-source acceptance and migration tests. Record the actual merged **integration SHA**, inputs, resulting coverage and independent other-AI review of interactions, schema/identity migrations, regressions and frozen Frank V1 decision/delivery boundary. Green source-branch CI is insufficient.
9. **Final overall independent Review after all planned modules are done**, before proposing any protected release. It must cover the entire product end-to-end, canonical acceptance checklist, source freshness and coverage, combined wallet holdings/history/funding, Dashboard real-user query, legacy compatibility/rollback, safety/notification boundaries, dependencies, actual tested merge SHA, open risks and proofs that no approved upstream feature regressed. Explicit final verdict and documented residual gaps required; a set of local module APPROVEs alone is not sufficient.
10. **Deploy only after separate, explicit user authorization** following production Mac read-only preflight, backups/rollback plan, isolated acceptance and final review; afterwards verify real local runtime, notifications, protected DB and postdeploy observations. Do not equate PR merge or Docs updates with production deployment approval.

## Immutable review ledger requirements

For *every module checkpoint*, append in its owning PR and canonical module review file:

| Required field | Meaning |
| --- | --- |
| module / task ID, stage | Exact F01, F02, A05, C02 etc., completed and pending criteria |
| reviewed code SHA, parent SHA, base branch | Do not review a moving PR name alone |
| reviewer and model / review date | If unverified, say so; external Review must not be represented as a native GitHub approval |
| result | `APPROVE`, `REQUEST_CHANGES` or `NOT_REVIEWED`; distinguish code from product acceptance |
| focused/full test runs and merged CI SHA | Source logs, actual outcomes, no skipped-failure claims |
| real/synthetic data provenance | Chain, slot, account, query, observed time, complete vs truncated |
| issue list and owner | Severity, reproduction, closing commit, exact retest/re-review |
| upstream and downstream impacts | API/schema/source identity/migration, frozen runtime compatibility, affected module re-review |
| remaining gaps / release authority | Live Mac/user flow, evidence coverage, rollback, explicit no-deploy while blocked |

A dependent feature must not silently replace upstream fields, contracts, DB identities or UI content. Any such change invokes **impact review** and combined regression, even if the new module's own tests pass. For distinct modules, schedule review at each completion checkpoint; do not let a backlog accumulate until all modules are done. After all modules pass, perform one **additional complete system Review**.
